# T-17: Error handling + retry layer

## Context

Currently, if `provider.stream()` throws (network error, 5xx, 429 rate-limit), the error bubbles up to `app.tsx` catch block and dispatches `SET_ERROR` immediately. No retry logic exists. The `StatusBar` already renders error state but without retry status.

This ticket adds a retry layer with exponential backoff around streaming calls.

## Files

**Create:**
- `src/streaming/retry.ts` — `withRetry(fn, opts)` wrapper
- `tests/retry.test.ts` — retry tests

**Modify:**
- `src/app.tsx` or `src/agent/agentLoop.ts` — wrap `provider.stream()` calls with `withRetry`
- `src/ui/StatusBar.tsx` — show retry status (attempt N/M) when streaming fails during retry

## Implementation details

1. `src/streaming/retry.ts`:

```typescript
export interface RetryOpts {
  maxAttempts?: number;       // default 3
  baseDelayMs?: number;       // default 1000
  maxDelayMs?: number;        // default 30000
}

export async function withRetry<T>(
  fn: () => Promise<T>,
  opts?: RetryOpts,
  onRetry?: (attempt: number, error: Error) => void,
): Promise<T>
```

Logic:
- Retry on: network errors (fetch/Axios), HTTP 5xx, HTTP 429 (Rate Limited)
- Do NOT retry on: 4xx (except 429), auth errors (401/403), validation errors
- On 429: if `Retry-After` header is present, respect it (up to 30s); otherwise use exponential backoff
- Exponential backoff: `baseDelay * 2^(attempt-1)` + jitter (±20%), capped at `maxDelayMs`
- `onRetry` callback fires on each retry attempt so the caller can update UI

2. Integration points:

**`src/app.tsx` `fetchResponse`** (chat mode):
- Wrap the `provider.stream(...)` call with `withRetry`
- On retry, dispatch an action that sets retry state
- Let the error still dispatch `SET_ERROR` after all attempts exhausted

**`src/agent/agentLoop.ts`:**
- Wrap `provider.stream(...)` with `withRetry`
- Pass an `onRetry` callback that can dispatch status updates
- IMPORTANT: The agent loop currently catches errors and dispatches `SET_ERROR`. The retry layer should sit BETWEEN the outer catch and the stream call, so retries happen silently (no error dispatched until all retries fail).

3. `src/ui/StatusBar.tsx`:
- Add `AppStatus` value `'retrying'` if it doesn't exist, or use a separate state field
- When retrying, show: `⚠ retrying (1/3)…` in yellow
- On success, revert to normal status
- On final failure, show error in red

4. Tests (`tests/retry.test.ts`):
- `withRetry` succeeds on first call → no retry
- `withRetry` fails × 2, succeeds on 3rd → retried twice, final success
- `withRetry` fails all 3 → throws after 3 attempts
- `withRetry` with 429 and Retry-After header → respects the delay
- `withRetry` with 401 → no retry, throws immediately

## Acceptance

- `npm test` — green
- `npm run build` — green
- Kill network mid-stream → UI shows "retrying (1/3)..." then resumes
- API returns 429 → retries with correct delay
- Auth failure → immediate error (no retry)
